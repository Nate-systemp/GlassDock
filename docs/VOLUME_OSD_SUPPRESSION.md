# Native volume OSD: prevent the keyboard trigger

Updated 2026-11-10. **Settings > Add Utilities > Hide Windows volume popup** remains optional and off by default. Safe/inspection modes leave it off.

## Root cause and replacement

The previous Flylet-inspired `SetWinEventHook` / `ShowWindowAsync(SW_HIDE)` backend reacted after the Shell presented its window. The user observed a split-second flash. An asynchronous post-show observer cannot guarantee zero rendered frames. That backend, its Shell request correlation timer and its 80 ms duplicate-event heuristic have been removed rather than accelerated.

`NativeVolumeOsdSuppression` now owns a dedicated message-pump thread and a `WH_KEYBOARD_LL` hook. It consumes only `VK_VOLUME_MUTE`, `VK_VOLUME_DOWN` and `VK_VOLUME_UP` before normal Shell dispatch. No foreign HWND is discovered, hidden, minimized, moved, restyled or polled. Explorer restarts and native OSD window recreation do not require rediscovery.

The callback only queues work to the existing `MasterVolumeService` MTA worker; it does not call COM, construct UI, wait for the UI dispatcher or run animations. Core Audio `VolumeStepUp` / `VolumeStepDown` apply endpoint-defined steps and unmute; mute reads and inverts actual `GetMute`. Commands retain the endpoint identity captured at acceptance so queued input cannot modify a replacement endpoint. The service reads actual volume and mute after applying the operation. `VolumeKeyHandled` then dispatches the existing HUD path, including at volume limits. Self-generated endpoint callbacks update the fill without starting another burst. Other applications' Core Audio changes continue to open the HUD through the original notification path.

Volume auto-repeat queues each step in order. Mute repeats are consumed without toggling mute repeatedly until release. Captured releases remain consumed if the option is disabled mid-press; the next gesture passes through. All other keys, including brightness, pass through. The service does not register hotkeys, inject/replay keys, change focus, change Windows settings or alter audio notifications.

## Recovery and limits

Disabling stops consuming new gestures. Disposal posts `WM_QUIT` to the hook thread, whose `finally` unhooks. Windows removes the process-owned hook after process termination; no persistent Shell mutation or recovery helper is required. The hook belongs to the normal interactive desktop and does not intercept the UAC/lock desktop.

Unavailable audio or failure to initialize the hook leaves normal Windows handling in place. A device disappearing after a key has already been accepted can prevent that queued command from applying; it is not replayed into Shell. Subsequent gestures fail open while audio is unavailable. Preserving working volume control takes precedence over suppressing its fallback UI.

This prevents native OSD requests generated by the intercepted volume-key path. OEM software, direct `WM_APPCOMMAND` senders, another audio application or a future Windows input path can independently request an OSD without producing these virtual keys. Doky does not claim to suppress those paths. A Windows low-level hook can also be silently removed if it exceeds the system callback timeout; keeping all COM/UI work off its dedicated thread avoids the previous UI-thread dependency but is not a universal system guarantee.

## Task Manager / elevated foreground fix (2026-11-10)

The normal-process volume hook did not cover the Task Manager foreground path. Volume capture now also runs in the existing protected elevated input helper's `WindowsKeyHook`, using the same `VolumeKeyCapture` policy. Only the three volume virtual keys are forwarded over the existing session pipe. The hook queues a channel record; it never waits for pipe I/O, audio COM or the UI thread.

The app sends `VOLUME|0` / `VOLUME|1` readiness independently of the existing keyboard state and recovery protocol. Capture is enabled only when the optional setting is on, the normal app has an available audio endpoint and its volume handler is installed. The helper advertises `CAPS|VOLUME1`. Old helpers ignore the optional control message and provide only normal-process coverage until updated. Old clients never enable capture on the new helper.

Forwarded events share the existing monotonic event sequence, expire after 500 ms, and validate their exact field count and allowed virtual-key range. The normal app's `MasterVolumeService` performs the operation and readback, so HUD notification origin, animations and endpoint handling remain the same. Since the first accepting hook consumes the key, the elevated and normal hooks do not both adjust volume. Helper disconnect/crash releases its hook through the existing lifecycle; the local hook remains the fallback. Lifecycle reset clears held-volume capture alongside existing keyboard state.

The helper payload was published and installed using the existing administrator-only `Install-InputHelper.ps1` into protected `C:\Program Files\Doky\InputHelper`, preserving the protected scheduled-task architecture. Installed EXE, helper DLL, Windows DLL and Core DLL SHA-256 hashes matched the built payload. Doky itself remains unelevated. The install completed successfully; a temporary wrapper's attempt to append to its still-open transcript failed afterward, so installation success was independently checked against the installed payload and the live `VOLUME1` capability rather than its wrapper exit code.

Verification: full ordinary Debug solution build **0 warnings, 0 errors**; **25 focused input-helper, volume-capture and audio tests passed**. After restarting the updated app and helper, a read-only observer recorded **10 actual Core Audio readbacks while Task Manager was foreground**, covering volume and mute, and **0 native host SHOW events** during the trace. The user tested first/held/rapid presses and mute/unmute with Task Manager open and confirmed **"No native popup; Doky's HUD and keys work."** No input-intercepting test helper was running during this integrated check.

This extends coverage to elevated applications on the normal interactive desktop. It does not alter the secure UAC/lock desktop, and it still requires the protected helper to be installed, updated and connected. Other OEM input paths and other Windows builds remain unverified.
